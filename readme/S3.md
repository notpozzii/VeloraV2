# Velora on S3

This package hosts the actual Velora interface, app pages, proxy JavaScript,
and service worker on S3. It does not load the desktop through a Cloudflare
iframe. The existing browser/proxy implementations and settings are reused.

## Build

From the repository, run:

```sh
bun install --frozen-lockfile
npm run export:s3
```

The output is `build/velora-s3.zip`. Extract it before uploading.
The regular `npm run build` still produces the Cloudflare Worker.

## Upload

Use a bucket you already own with public read access configured for its website
files. From the extracted package, with the AWS CLI signed into your account:

```sh
bash upload-s3.sh velorastudy
```

This uploads the complete `site` folder and creates exact object keys such as
`/slate`, `/api`, and `/settings`, with the correct HTML content type. S3 does
not automatically rewrite those URLs. Merely uploading `index.html` will leave
the apps and browser broken. The script does not delete other bucket objects
or change bucket permissions.

Then open:

```text
https://velorastudy.s3.us-east-2.amazonaws.com/index.html
```

Use HTTPS. The HTTP S3 website endpoint cannot run the required service worker.
The `os.html`, `slate.html`, and `api.html` filenames also work when opened
directly. The package must be hosted at the bucket root, not inside a subfolder.

## Dependencies and limits

- Web browsing still needs the configured external Wisp WebSocket relay. S3
  cannot host that relay. Browser and GeForce NOW use
  `wss://system.pilotrights.com/jsonn/` by default. A saved custom server still
  overrides this default.
- Registering a custom domain through `/api/byod` needs Cloudflare's server
  and credentials; the S3 version explains this rather than submitting to S3.
- Games and Pyrite are optional assets missing from the current repository
  (`static/books/gmes.json` and `static/pyrite/index.html`). Add the licensed
  app assets to those folders before exporting to include them. The manifest
  reports these omissions. The hosted site currently returns 404 for them too.
- The existing HTML/SVG wrapper downloads remain available and still depend
  on the hosted Velora site. This ZIP is the standalone hosting package.
- Network filtering and third-party availability depend on the network and
  remote services. Hosting locally on S3 does not guarantee access.

To preview the exported object routes locally:

```sh
node scripts/preview-s3.mjs
```

Open `http://localhost:5197/index.html`. Localhost supports service workers;
ordinary HTTP hosts do not.


## Automatic updates from GitHub releases

The workflow in `.github/workflows/main.yml` builds this S3 package and uploads
it to `velorastudy` when a stable GitHub release is published. You can also run
**Deploy Velora to S3** manually from the Actions tab. Ordinary pushes and
prereleases do not deploy the site.

The configuration targets `notpozzii/VeloraV2`, region `us-east-2`, and the
GitHub environment `s3-production`. The workflow replaces the inherited GitLab
mirror; it does not send source to GitLab.

### One-time AWS setup

1. Sign into the AWS account that owns `velorastudy` and open CloudShell.
2. Upload `scripts/setup-s3-github.py` and `scripts/s3-github-config.json` into
   the same CloudShell folder. From that folder, preview the changes:

   ```sh
   python3 setup-s3-github.py
   ```

3. Apply the dedicated deployment role:

   ```sh
   python3 setup-s3-github.py --apply
   ```

   This checks bucket ownership, creates or reuses GitHub's OIDC provider, and
   creates `VeloraGitHubS3Deploy`. It prints `AWS_ROLE_ARN=...`. It uploads no site
   files and does not change bucket permissions. It refuses to overwrite an
   unrelated role with the same name.

4. In GitHub, open **Settings → Environments**, create **s3-production**, and add
   an environment **variable** named **AWS_ROLE_ARN** with the printed ARN as
   its value. The role ARN is not an AWS secret key. No AWS access keys go in
   GitHub or this repository.
5. Configure that environment to allow deployments from `main` and release
   tags matching `v*`. Use a `v` prefix for release tags, such as `v1.3.1`.
6. Open **Actions → Deploy Velora to S3 → Run workflow**, choose `main`, and run
   it once. A successful run links to the updated S3 site.

The role's trust names this exact repository and production environment,
including the immutable GitHub owner and repository IDs. A renamed or
transferred repository needs a reviewed configuration update. The role can
list, read, and upload objects only in this bucket. It cannot delete objects,
change bucket policy, or manage IAM.

### Subsequent updates

Commit the intended release changes to GitHub, then publish a stable release
from a `v*` tag. The workflow builds and checks the site, transfers the checked
package between jobs, obtains temporary AWS credentials only in the deployment
job, and runs the generated S3 uploader. Assets upload before HTML. Existing
bucket files are not deleted. Your Mac does not need to stay running.

GitHub Actions must finish successfully before calling the S3 copy updated.
Publishing the separate Sites deployment does not trigger this workflow.

References: [GitHub OIDC on AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws),
[AWS S3 sync](https://docs.aws.amazon.com/cli/latest/reference/s3/sync.html).
